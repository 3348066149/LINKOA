## 四、本次发现并修复的缺陷

### 🔴 P0-1：客户在审核弹窗中无法上传任何文件（功能性阻断）

**现象**：客户打开审核弹窗，点「上传文件」必然失败，提示"文件上传失败"。客户反馈附件功能完全不可用。

**根因**：前端 `client/Project.vue` 的 `onReviewUploadFile` 复用了设计师侧接口 `uploadFormImage()`，即 `POST /api/projectNode/formImage/upload`。该接口的权限依赖是 `require_not_customer()`，客户账号**必然**被 403 拦截。与此同时，专为客户设计的 `/api/review/upload` 接口在前端**从未被调用**（只有一行未使用的 `reviewUploadUrl` 常量）。

**验证证据**：测试 D3 返回 `code=403 "客户账号为只读权限，禁止修改"`。

**修复**：
- 新增前端 API `uploadReviewFile(file, projectNodeId)` 指向 `/review/upload`
- 客户审核弹窗改走该接口，并修正响应字段读取（客户接口返回 `path`，设计师接口返回 `imagePath`）
- 一并清理了已失效的旧代码（`beforeReviewImageUpload` / `onReviewImageSuccess` / `onReviewImageError` / 未使用的 `reviewUploadUrl`）

### 🟠 P1-2：表单文件值含 null 项会导致页面白屏

**现象**：当表单文件字段的 JSON 值含 `null` 项（如 `[null,"a.png"]`）时，`isFormImg(null)` 内部执行 `null.split('.')` 抛异常，导致**整个项目详情页 / 客户门户页面白屏**。

**验证证据**：Node 复现确认 `parseFormFiles('"[null,\"a.png\"]"').filter(isFormImg)` 抛 `Cannot read properties of null (reading 'split')`。

**修复**：统一加固三处解析函数（`Detail.vue` 的 `parseFormFiles`、`client/Project.vue` 的 `parseFiles`、`DynamicForm.vue` 的 `getFiles`），在源头过滤掉非字符串与空串项。

### 🟡 P1-3：后端上传实现存在三处隐患

在 `node_service.upload_form_image` 中发现并修复：

1. **常量与文案不一致**：`MAX_FORM_FILE_SIZE = 1GB`，但报错文案写的是"超过 100MB 上限"。已统一为 100MB。
2. **超限时残留半截文件**：原实现在 `with open()` 块内抛异常，若被外层捕获则文件句柄未关、半截文件残留。已改为先 `close()` + `_remove_file()` 再抛。
3. **空文件无校验**：0 字节文件会被当作成功保存。已补"上传文件内容为空"校验。
4. **危险扩展名清单不全**：补充 `.mjs .aspx .msi .com .scr .jar`。

同时把上传逻辑抽取为公共函数 `save_upload()`，由设计师侧与客户侧共用，消除两份重复实现。

## 五、⚠️ 上线前必须处理（未改动，需你确认）

### 1. `JWT_SECRET` 仍是开发默认值（高风险）

启动日志持续告警：

> 【安全警告】JWT_SECRET 仍是开发默认值，任何人都能伪造管理员 token。生产环境必须在 backend/.env 中配置 JWT_SECRET=`<随机 32 字节以上字符串>`。

**影响**：知道默认值的人可自行签发任意角色（含管理员）的 token，等于鉴权体系失效。
**建议**：上线前在 `backend/.env` 写入随机长字符串。生成命令：
```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```
> 注意：`backend/.env` 已在 `.gitignore` 中，改完不会进版本库，安全。

### 2. 上传大小上限的业务确认

单个文件上限 100MB 是本次统一后的值。若实际业务会传更大素材（如原始视频），需调大 `MAX_FORM_FILE_SIZE`；同时建议确认 **Nginx / 反代是否也有 body 大小限制**，否则前端会看到 413 而非友好提示。

## 六、其他需要你知道的情况

### 1. 三个历史测试脚本已过时（非产品缺陷）

`check_dept_role_split.py`、`check_role_api.py`、`check_dept_client_api.py` 测试的是**已被移除**的"部门即权限模板 / 多角色（设计师·设计总监·行政）"模型。现行模型（V1.4.15 起）用户角色已收敛为 `管理员 / 普通 / 客户`，部门仅作组织归属。

这三个脚本会因 `role` 取值非法而失败，**属预期，不是系统 BUG**。我已在文件头标注 `[已过时-不可运行]` 并写明替代覆盖位置。它们的功能已被 `full_flow_check.py` 对应章节覆盖。

### 2. 两个封面测试原本会污染真实数据（已修复）

`check_cover_api.py` / `check_customer_cover_api.py` 原先直接取 `items[0]`（即你真实项目列表的第一条）上传并移除封面——会在**生产项目上做写操作**。已改为：
- 自建隔离的测试项目/客户/单位，测完自动删除
- 封面移除步骤对"环境删除守卫"容错，改以数据库字段是否清空判定业务结果

### 3. 关于日志里的 HTTP 500

运行测试时你会在 `server_restart.log` 看到个别 `500 Internal Server Error`（如 `cover/remove`、`attachment/delete`）。**这不是系统缺陷**，而是当前沙箱环境对 `os.remove` 挂了批量删除保护钩子（`sitecustomize.py` 抛 `SystemExit`）导致的。证据：同一请求中**数据库字段已正确清空**，仅物理文件删除被拦。在正常部署环境（无此钩子）不会出现。测试脚本已做容错处理，避免误判。
