# LINKOA V1.4.9 AI 助手「青青侠」改造方案

> 状态：待确认（用户已拍板：联网搜索走 DeepSeek 内置搜索；本文档为实施前的设计定稿）
> 日期：2026-09-02

---

## 0. 一句话结论

当前「青青侠」有两个层面的问题：**①安全/身份层**——AI 不知道"当前用户是谁、归属哪家公司"，会反问"你的公司名称是什么"；**②幻觉层**——本地项目库检索为空时没有兜底约束，导致大模型用训练记忆编造项目或把外部常识（如真实存在的"青岛地铁公司"）当成内部数据。本方案通过 **①身份绑定与数据隔离 ②空检索兜底 ③联网搜索开关 ④来源标注** 四层改造根治，并顺带修复两个前端 bug（青青侠图标位移频闪、会话列表删除按钮改为三点菜单）。

---

## 1. 问题诊断（已确认根因）

### 1.1 幻觉：编造「智能物流平台升级」等 3 个假项目

调用链路：

```
用户问话 → retrieve_projects() 检索本地项目 → 检索到就喂给模型 / 检索为空就什么都不喂 → 模型回答
```

- 系统里项目列表为空（用户在项目列表里看不到，正是证据）→ 检索结果为空。
- `ai_service._build_messages()` 里，当 `context == ""` 时**不注入任何约束**（`if context:` 才追加）。
- 模型只拿到"你是青青侠"的人设 + 问题，为满足"查项目"意图，用训练记忆脑补了 3 个假项目。

**本质**：system prompt 里的"绝不编造"只约束"有数据时别瞎加"，没约束"无数据时怎么办"。

### 1.2 知识来源混淆：把「青岛地铁」当成本公司项目

同一根因：本地检索"青岛地铁"无匹配 → context 为空 → 模型退回到训练知识里真实存在的"青岛地铁公司"作答，把外部常识当成了内部数据。**不是模型想联网，是"无本地数据"时它分不清该说"没查到"还是"用常识硬答"。**

### 1.3 关键词提取缺陷

`llm/retriever.py:_extract_keywords()` 用 `re.split` 按非中英文数字切分，再取 `2 <= len <= 12` 片段。像「我们公司最近有哪些项目在进行」这种 14 字无标点整句，**提不出任何关键词**，只能回退到"最近更新项目列表"，而列表又是空的。

### 1.4 反问"你的公司名称是什么"（安全红线，用户最新补充）

调用链路上，`chat_stream()` 虽然拿到了 `current_user`，但 `_build_messages()` 的 system prompt **只写了"你是谁（青青侠）"，没写"用户是谁"**。于是模型判断不了提问者身份/归属时，会反问"我需要确认一下你的公司名称哦"。

**这是安全红线**：公司名称早已和账号绑定（内部账号 = 本公司；客户账号 = 其归属公司），AI 不该问、也不能问。问出口的后果：

1. 暴露"AI 没接住身份"的缺陷，体验差；
2. 诱导客户自报家门，把本应由系统托底的身份识别丢给用户；
3. 极端情况下客户报错公司名，还可能带来误导甚至越权访问的隐患。

必须从根上杜绝：**把身份上下文注入 prompt + 加"严禁反问身份"硬约束**，让 AI 从一开始就知道"你是谁、能看什么"，而不是反过来问用户。

## 3. 方案〇：身份绑定与数据隔离红线（最高优先级）

### 3.1 现状核实（已确认）

身份与隔离链路现状如下（`models/user.py`、`services/user_service.py`、`dependencies.py`、`services/llm/retriever.py`）：

| 账号类型 | `sys_user` 判定依据 | 归属公司来源 | 项目可见范围（现状） |
|---|---|---|---|
| 内部员工 | `role != "客户"` 且 `dept_id` 非空 | 本公司（青岛领客文化传播有限公司） | 全量（`retriever` 不加过滤） |
| 客户账号 | `role == "客户"` 且 `customer_id` 非空 | `customer_id → customer.category_id → customer_category.category_name` | `retrieve_projects` 已按 `Project.category_id == cat_id` 严格隔离 ✅ |

**结论：数据隔离的地基已经在 `retriever.py` 里搭好了**（客户账号检索时强制 `category_id` 过滤，员工全量）。真正的缺口是——**身份没有注入到 prompt**，所以 AI 才会反问公司名。也就是说，"隔离能拦住数据"，但"AI 不知道自己是谁、于是去问用户"。

### 3.2 修复方案：身份上下文注入 + 严禁反问

在 `ai_service.py` 新增身份解析函数，并把身份声明注入 system prompt：

```python
def _resolve_identity(db, current_user) -> dict:
    """返回 {is_internal, company_name}；客户账号解析归属公司名（与 retriever 口径一致）"""
    if current_user.get("role") == "客户" and current_user.get("customer_id"):
        cust = db.get(Customer, current_user["customer_id"])
        if cust is not None:
            cat = db.get(CustomerCategory, cust.category_id)
            return {"is_internal": False, "company_name": cat.category_name if cat else "未知"}
    return {"is_internal": True, "company_name": "青岛领客文化传播有限公司"}
```

在 `_build_messages()` 追加一条**身份 system 消息**（独立成条更清晰）：

- 内部员工：
  > "你正在服务的是本公司（青岛领客文化传播有限公司）的内部员工。可以正常回答关于本公司全部项目的问题。"
- 客户账号：
  > "你正在服务的是【{company_name}】的对接人。你**只能**查看并回答关于【{company_name}】的项目信息，**严禁**透露任何其他公司的项目/客户/进度/金额信息。"

并在主 system prompt（`DEFAULT_AI_SYSTEM_PROMPT`，见 4.4 节）追加一条**硬约束**：

> "严禁询问用户所在公司/单位名称、身份、账号等任何可通过账号绑定得知的信息；这些信息系统已在后台根据登录账号自动注入，你直接据此作答即可。"

### 3.3 为什么这是"根上"的修复

- 反问的根因是"模型不知道用户身份"，注入身份上下文后它没有反问的动机。
- 数据隔离（`retriever`）管住"能查到什么"，身份 prompt 管住"模型是否知道自己该答什么、不该答什么"——两者双保险。
- 即使模型被诱导（如客户问"我还有别的公司的项目吗"），客户账号的检索结果里也只有本公司项目，模型无从答起，从数据源层面兜底。

> 备注：`get_current_user()` 目前返回 `{id, username, real_name, role, dept_id, customer_id, is_enable}`，**不含 company_name**（只有登录时 `_user_info` 才返回）。为避免影响其它接口，不在 `get_current_user` 上动，改在 `ai_service` 内按需解析归属公司，隔离与身份共用同一套 `customer_id → category_id` 解析逻辑。

## 4. 方案一：根治幻觉（后端）

### 4.1 空检索时注入"无数据"强约束

`backend/app/services/ai_service.py` 的 `_build_messages()` 改为：无论 `context` 是否为空，都注入一条数据边界 system 消息：

- `context` 非空：沿用现有逻辑（"仅基于这些数据回答，不要编造"）。
- `context` 为空：注入——
  > "系统内**未检索到任何相关项目/客户/节点数据**。你必须如实告知用户『没有查到相关数据』，**严禁编造**任何项目名称、客户、进度、节点、金额等具体信息，也不得使用外部常识或训练记忆补造。"

### 4.2 业务查询类问题检索为空时直接短路（不调 LLM）

在 `chat_stream()` 里，`retrieve_projects()` 返回空时，判断问题是否属于**业务查询**（命中关键词：项目/进度/客户/节点/状态/对接人/立项/交付/阶段/流程 等）。命中则直接 `yield` 一条固定话术并结束，**不调用 LLM**：

> 例："我在系统里没查到相关项目哦～确认一下项目名称，或者到「项目」列表里看看有没有漏掉的～"

好处：100% 杜绝幻觉、省 token、响应快。闲聊类问题（如"你好""讲个笑话"）不受影响，仍正常走 LLM。

### 4.3 优化关键词提取

`llm/retriever.py:_extract_keywords()` 增加**业务停用词表**（我们/你们/公司/贵司/最近/哪些/什么/怎么/多少/有/在/进行/的/项目/状态/进度 等），先剔除停用词再切分，让「我们公司最近有哪些项目在进行」这类问法也能正确落回"最近更新项目列表"（该列表本身再叠加"进行中"状态过滤，见 4.4）。

### 4.4 强化默认人设 prompt

`backend/app/main.py` 的 `DEFAULT_AI_SYSTEM_PROMPT` 第 1 条改为：

> "1. 业务问题**只能**依据系统提供的项目数据回答；**系统未提供的数据一律回答『没查到』，绝不臆造**，也不得引用外部常识/训练记忆充当公司内部信息；"

并追加身份硬约束（见 3.2）。

> 注意：改的是默认值，存量库（`ai_config` 表已存在记录）不会自动更新，需管理员在「AI 设置」面板同步改，或提供一次性迁移。

## 5. 方案二：联网搜索开关（DeepSeek 内置搜索）

### 5.1 交互语义（按用户诉求："区分本地知识库 vs 联网"）

| 开关状态 | 数据来源 | 回答标注 |
|---|---|---|
| **关闭（默认）** | 纯本地项目库（RAG），检索为空就"没查到" | 无（或"引用自系统项目"） |
| **打开** | 联网搜索（DeepSeek 服务端 web_search），不查本地 | "联网搜索"标签 + 提示"结果来自互联网，可能与贵司无关" |

> 说明：采用"来源切换"语义（开=联网、关=本地），最清晰，也最贴合用户"区分知识库"的诉求。后续如需"本地优先 + 本地无则联网"的混合语义，可在此基础上扩展，本次不做。

### 5.2 技术事实

- DeepSeek 的 **Chat Completions 接口没有内置联网搜索**；联网能力在 **Responses API**（`POST /responses`）里，通过 `tools: [{"type": "web_search"}]` 开启，服务端一次请求内自动"搜索→打开网页→生成答案"，目前要求模型为 **`deepseek-v4-flash`**。
- 因此方案二与"附：模型升级"绑定：联网开关要真正生效，模型需升级到 `deepseek-v4-flash`。

### 5.3 后端改动

1. `backend/app/schemas/ai.py`：`ChatStreamRequest` 增加 `web_search: bool = Field(default=False)`。
2. `backend/app/services/llm/deepseek.py`：新增方法 `stream_chat_with_search(messages)`，走 `POST https://api.deepseek.com/responses`：
   - body：`{ "model": "deepseek-v4-flash", "input": <messages 数组>, "tools": [{"type": "web_search"}], "stream": true }`
   - 流式解析：`response.output_text.delta` 取增量文本；`response.completed` 结束；`response.failed`/`error` 转错误。
   - （事件字段以官方 Responses API 文档为准，实施时先做一次探测确认。）
3. `backend/app/services/ai_service.py` 的 `chat_stream()`：`web_search=True` 时**跳过本地 RAG**，直接调 `stream_chat_with_search`，sources 置空、并给 done 事件加一个 `webSearch: true` 标记。
4. `backend/app/routers/ai.py`：无需改路由，入参 schema 已覆盖。

### 5.4 前端改动

1. `frontend/src/components/ai/ChatInput.vue`：在输入框下方加一个「联网搜索」`el-switch`（默认关，带小地球图标 + 文案"联网搜索"）。
2. `frontend/src/stores/ai.js` 的 `sendMessage(message, { webSearch })`：透传给 `chatStream`。
3. `frontend/src/api/ai.js` 的 `chatStream`：body 加 `webSearch` 字段。
4. `frontend/src/components/ai/MessageList.vue`：读取 done 事件的 `webSearch` 标记，给该条 assistant 消息打"联网搜索"标签。

## 6. 方案三：来源标注（前端）

`MessageList.vue` 在每条 assistant 消息下方，根据状态显示小标签：

- `sources` 非空 → 绿色/蓝色小标签「引用自系统项目」，点击可跳转（后续可做）。

## 7. Bug 修复 A：青青侠图标位移 + 频闪

### 7.1 根因

`frontend/src/components/ai/MascotFloat.vue` 的 `.mascot` 按钮**同时**挂了：

- `animation: mascot-float 3.2s infinite`（用 `transform: translateY` 上下浮）
- `transition: transform 0.25s`
- hover 态 `.mascot.hovered` 把 animation 换成 `mascot-shake 0.55s`（单次、无 `infinite`、无 `forwards`）+ `transform: scale(1.12)`

三个后果：

1. **位移突变**：hover 瞬间 animation 从 `translateY` 浮动切到 `rotate/scale`（无 translateY），图标从"当前浮动偏移位置"跳回 `translateY(0)`，垂直跳动明显；0.55s 后动画结束再次回落。
2. **频闪**：`mascot-shake` 无 `infinite`/`forwards`，0.55s 后 animation 结束、transform 交还给 hovered 的静态 scale；叠加 `transition` 与 `animation` 同争 transform、鼠标在图标边缘抖动反复增删 `hovered`，`mascot-float`/`mascot-shake` 来回切换 → 频闪。
3. **触摸设备**：`@mouseenter/@mouseleave` 在触屏上 tap 只触发 enter、leave 不触发（或延迟），导致 hovered 卡住、气泡不消失。

### 7.2 修复方案

1. **动画分层**：把 `mascot-float` 上下浮动动画移到**外层容器**（`.mascot-wrap` 或新增 `.mascot-float` 包裹层），内层 `.mascot` 不再有 float 动画——让"浮动"和"hover 反馈"作用于不同元素，彻底消除 transform 冲突。
2. **hover 反馈改用 transition**：`.mascot` 只保留 `transition: transform`，`.hovered` 只做 `transform: scale(1.12) rotate(-3deg)`，不再切换 animation。shake 效果如要保留，放到外层或改成一个**带 `forwards`、且不覆盖 translateY** 的动画；最简单是去掉 shake，仅 scale + 轻微 rotate 的 transition。
3. **触屏适配**：把 `@mouseenter/@mouseleave` 改为 `@pointerenter/@pointerleave`（同时覆盖鼠标与触屏），或补 `@touchstart/@touchend`，确保 tap 后气泡能收起、hovered 能复位。
4. 保留 `prefers-reduced-motion` 降级。

## 8. Bug 修复 B：会话列表三点菜单（置顶/重命名/删除）

### 8.1 需求

删除按钮由「垃圾桶图标」改为「三个点（⋯）」；点击弹出下拉菜单：**置顶、重命名、删除**，其中**删除为红色图标 + 红色文字**。

### 8.3 前端改动

## 9. 顺带：deepseek-chat 弃用升级

- 现状：`backend/.env` 里 `AI_MODEL=deepseek-chat`。
- 问题：DeepSeek 官方已把 `deepseek-chat` / `deepseek-reasoner` 标记为 **2026/07/24 弃用**，推荐 `deepseek-v4-flash`（非思考）/ `deepseek-v4-pro`。
- 建议：`.env` 改为 `AI_MODEL=deepseek-v4-flash`（同时是联网搜索的前提）；`ai_config` 表里已存在的那条记录也需在「AI 设置」面板同步改模型名，或提供一次性迁移。

## 12. 待确认/风险

- **联网开关语义**：已按"来源切换"设计（开=联网、关=本地）。如需"本地优先+本地无则联网"的混合语义，请指出，实施时调整。
- **Responses API 流式事件字段**：以 DeepSeek 官方文档为准，实施前先探测一次。
- **存量 `ai_config` 记录**：system prompt 与 model 的默认值改动不会自动覆盖存量记录，需在「AI 设置」面板手动同步或加一次性迁移（建议后者）。
- **内部员工可见范围**：现状是内部员工全量可见所有项目（含全部客户单位）。若内部也需要按部门/项目细分权限，属超出本次范围的增强，需另行确认。
